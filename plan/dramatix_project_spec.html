00 · 專案願景

為什麼需要「策略 Agent」作為前置層？

現有的 AI 劇本系統有一個根本性的問題：框架是由使用者選擇的，而大多數使用者並不是編劇。這個前提假設既不合理，也不可擴展。DRAMATIX 的核心主張是：框架選擇本身也是一個可以被 AI 完成的推理任務，而且這個推理步驟應該對使用者透明、可調整。

🎯

問題：框架選擇的認知負擔

要求使用者在輸入主題前先學會 Save the Cat、英雄旅程、麥基框架，等同於要求病患在就診前先學會診斷學。策略 Agent 應該扮演「敘事診斷師」的角色，而非讓使用者自學。

⚡

解法：框架 DNA 的動態合成

不同主題天然對應不同框架組合比例——「電流大戰」需要 70% 英雄旅程 + 30% 麥基電荷；「深夜的 LINE 訊息」需要 60% STC + 40% 麥基鴻溝。這個比例配方就是「Framework DNA」。

🤝

設計原則：透明但不繁瑣

使用者確認環節必須是「導演簡報」而非「技術審查」——系統展示策略的效果（「這個組合會讓故事在中點產生最大的情感翻轉」），而非暴露底層的技術細節。

01 · 系統架構

雙層架構：策略智能層 ＋ 故事生成層

系統分為兩個根本不同性質的層次：策略層負責「如何講」的決策，生成層負責「把它講出來」的執行。兩層之間只有一個使用者確認點，保持流程的流暢性。

設計見解
為什麼只有一個使用者確認點？多個確認點是常見的設計陷阱——每一次打斷都會破壞「敘事動量」（Narrative Momentum）。使用者應該在故事開始之前確認方向，而非在過程中不斷被要求微調。這也是為什麼確認閘道（Confirmation Gate）的設計至關重要：它呈現的必須是足夠有意義的資訊，讓使用者能做出真正有依據的決定，而非流於形式的點擊確認。
02 · 策略智能層

Phase 1：Theme Intelligence → Framework DNA

策略層是 DRAMATIX 的「編劇顧問大腦」。它在 3 個步驟內完成從原始主題到可執行框架配方的推理，並以「導演簡報」的形式呈現給使用者確認。

S1
主題分析器（Theme Analyzer）
將自然語言主題轉換為多維度向量

使用者輸入的主題往往是模糊的自然語言（「我想做一個關於背叛的故事」）。分析器的工作是將其拆解為結構化的敘事維度向量，作為框架選擇的依據。

# 主題分析器輸出的結構化維度向量（示例） ThemeDimension { medium: "youtube_short_doc", # 媒介推斷 tone: "suspense_horror", # 情緒基調 protagonist_type: "everyman", # 主角原型 conflict_axis: "external_mystery", # 衝突軸 time_scope: "contemporary", # 時間範圍 truth_complexity: 0.7, # 0=單純, 1=高度複雜 emotional_depth: 0.6, # 心理刻畫需求 pace_requirement: 0.8, # 節奏密度需求 myth_resonance: 0.3, # 神話原型共鳴度 knowledge_transfer: 0.2 # 知識傳遞比重 }

媒介推斷

從敘述風格、目標長度暗示、主題類型自動推斷最可能的發佈媒介（YouTube、Podcast、影集、短片等）

衝突軸分析

辨識故事的核心張力來源：外部衝突 vs 內部衝突、人 vs 人 vs 社會 vs 自然，決定框架的情緒走向

神話共鳴度評分

衡量主題是否具備神話原型的深層結構（英雄、陰影、導師），決定英雄旅程框架的參與比重

S2
策略合成器（Strategy Synthesizer）
基於維度向量輸出 Framework DNA 配方

策略合成器是整個系統的核心推理引擎。它接收維度向量，透過規則 + LLM 推理的混合方法，為每個框架分配「使用權重」，並說明各框架在這個特定故事中扮演的角色。

S3
確認閘道（Confirmation Gate）—— 唯一的使用者觸點
以「導演簡報」呈現策略，使用者進行輕量確認或微調

確認閘道的設計哲學：讓使用者感覺自己是導演，而非系統工程師。呈現的資訊必須是敘事效果的描述，不是框架名稱的清單。

───────────────────────────────────────────── DRAMATIX 策略簡報 // 主題：「特斯拉 vs 愛迪生」 ───────────────────────────────────────────── 媒介推斷： YouTube 歷史紀錄片（8-15 分鐘） 故事核心： 「一個天才的信念如何在背叛中淬煉成更強大的形式」 情感弧線： 理想主義 → 破碎 → 新生 → 孤獨的勝利 關鍵設計決策： ✦ 中點（50%）：愛迪生的「美國式幽默」承諾欺騙 → 電荷從 +++ 翻轉為 ---，最大鴻溝 ✦ 英雄的缺陷：相信聰明足以換得公平 → 整個旅程是這個信念的破碎與改寫 ✦ 結局電荷：勝而憂（非純粹勝利） → 避免英雄主義的廉價收尾 預計輸出節拍數： 12 估算字數： 3,200–4,500 字 ────────────────────────────────────── [ 確認並開始生成 ] [ 調整策略方向 ] [ 重新輸入主題 ]
設計陷阱警告：確認介面如果暴露太多技術細節（「Save the Cat 65% + McKee Gap 30%」），會讓非編劇使用者感到困惑並產生不必要的微調衝動。應當只展示敘事效果層的描述，讓使用者確認的是「這是我想要的故事走向嗎」，而非「這個框架比例是否最優」。
03 · 故事生成層

Phase 2：Agent Crew 的協作生產流程

確認閘道通過後，系統將 Framework DNA 注入 Agent Crew，開始協作生成。關鍵設計是：每個 Agent 只看到它需要看到的信息，避免「指令飽和」導致的品質下降。

G1
編制代理人（Orchestrator）—— 動態場景任務分配
根據 Framework DNA 拆解大綱並動態調度其他 Agents

Orchestrator 接收 Framework DNA 後，首先生成「故事骨架」（Scene Map），將整個結構拆解為獨立場景任務，然後根據每個場景的性質決定需要調用哪些 Sub-Agents。

❌ 傳統單一 Agent 模式

一個 Prompt 塞入全部指令，導致「指令飽和」
無法在長篇生成中維持角色一致性
Scene Energy 檢查與生成混合，互相干擾
框架邏輯與對白生成搶占同一上下文窗口

✓ DRAMATIX 多 Agent 模式

Orchestrator 管理宏觀結構，Sub-Agents 聚焦微觀任務
角色建築師維護獨立的角色記憶空間（Story Bible）
Energy Monitor 作為獨立異步進程運行
對白暗殺者作為最後一道 Pass，不干擾生成流程
設計見解 · 關於 Orchestrator 的核心挑戰
Orchestrator 最困難的任務不是分配工作，而是決定「何時讓故事自由發展」。框架是藍圖，不是鐵籠——當 Scene Simulator 在即興演練中產生了一個比框架更好的對話走向，Orchestrator 必須有判斷力去「接受偏差」並更新場景地圖，而非強制拉回框架節點。這需要在 Orchestrator 的指令中明確建立「框架彈性容差」的概念。

05 · 使用者體驗流程

從輸入到輸出：使用者只做三件事

複雜的多 Agent 協作應該對使用者完全透明。使用者體驗的目標是：讓他感覺自己在和一個「非常聰明的編劇助理」對話，而非在操作一套複雜的系統。

01
輸入主題
任意形式的自然語言描述。「一個關於背叛的故事」「特斯拉 vs 愛迪生」「深夜的 LINE 訊息」均可接受。
›
02
等待策略分析
系統自動完成主題分析 + 框架合成，約 15–30 秒。使用者看到進度提示，但不看到技術細節。
›
03 ★
確認導演簡報
閱讀策略摘要（故事核心、情感弧線、關鍵轉折點描述），選擇「確認」或「微調方向」。
›
04
等待故事生成
Agent Crew 開始協作生成。可選擇「串流顯示」（邊生成邊閱讀）或「完成後顯示」。
›
05
接收輸出
劇本全文 + 故事聖經（角色檔案、電荷歷史、框架決策紀錄），可進一步要求「修改某個場景」。
設計見解 · 「微調方向」的邊界
使用者在確認閘道選擇「微調方向」時，應當只能調整敘事效果層的參數——例如「我希望結局更悲劇一些」或「我希望主角更有缺陷感」——而非框架技術層的參數。系統接收這些自然語言調整後，由策略合成器重新計算 Framework DNA，再次呈現導演簡報。這個迴圈最多允許 2 次，避免使用者陷入無限調整的決策疲勞。

07 · 風險評估

已知設計風險與緩解策略

風險項目 等級 問題描述 緩解策略
框架剛性 高 Agent 過度服從框架節點，產出「公式感」強的劇本，反而強化 AI 味 在 Orchestrator 中建立「彈性容差」機制；Framework DNA 的節拍位置有 ±10% 的浮動空間；Scene Simulator 在即興演練時完全不知道框架節點
上下文窗口耗盡 高 長篇劇本生成時，Historian 記錄的 Story Bible 過大，超出 LLM 上下文限制 向量數據庫 + 語義檢索（只提取當前場景相關的記憶片段）；Story Bible 採用「壓縮摘要 + 詳細索引」雙層結構
策略誤判 中 主題分析器對模糊主題的維度向量化產生偏差，導致框架選擇失準 確認閘道作為糾錯機會；允許「調整方向」的 2 次迴圈；記錄誤判案例用於持續改進分析器
對白暗殺者過度干預 中 Dialogue Assassin 修改力度過大，破壞了生成層的原有情感節奏 設定「修改強度」參數（輕度 / 中度 / 重度）；每次修改記錄 diff，支持 Orchestrator 回退

09 · 設計見解與建議

我認為最值得關注的五個設計決策

見解 01 · Dialogue Assassin 應該是「最後一道門」而非「內建流程」
大多數系統設計會傾向將對白品質控制嵌入生成流程的每一步。我認為這是錯的——它會讓生成代理人在創作時過度自我審查，反而產生更平淡的初稿。正確的設計是：讓 Scene Simulator 先「盡情發揮」，然後讓 Dialogue Assassin 在後處理階段進行手術。「創作自由」和「品質控制」應該分離在不同的時間節點，而非同時發生在同一個 Agent 上。
見解 02 · 敘事歷史學家（Historian）是整個系統最被低估的 Agent
在多數多 Agent 系統的討論中，Historian 類型的 Agent 往往被視為「記帳員」而非關鍵角色。但在敘事生成系統中，跨場景一致性的維護難度遠超過單場景的生成品質。一個角色在第一場景說「我永遠不會原諒你」，卻在第七場景輕描淡寫地和解——這種邏輯漏洞是讓讀者出戲的最快路徑。Historian 應當有自己的向量數據庫和主動的一致性校驗機制，而非只是被動地紀錄。
見解 03 · Framework DNA 應該允許「框架空缺」
有時候最好的策略是在某個特定的故事段落不使用任何框架——讓場景純粹由角色的內在邏輯驅動，而非被節拍百分比約束。建議在 DNA 配方中加入一個 "free_zones" 欄位，標記哪些場景允許 Orchestrator 放棄框架干預。這類似於爵士樂的「即興橋段」概念——結構存在，但在特定節點完全交給演奏者。
見解 04 · 使用者確認不應該是「批准」，而應該是「方向確認」
確認閘道的心理設計很重要：如果使用者感覺自己在「批准一個技術方案」，他們會焦慮並傾向過度干預；如果他們感覺在「告訴導演自己想要什麼感覺的電影」，他們的輸入會更高品質且更具創意。確認閘道的文案措辭、視覺呈現方式，以及「微調」選項的顆粒度，都應服務於這個心理設計目標。
⚠ 最大的潛在誤區：把「更多 Agent」等同於「更好的品質」。 系統設計的誘惑是加入越來越多的專業 Agent（風格 Agent、格式 Agent、事實核查 Agent...）。但每新增一個 Agent 都會增加協調成本、延長生成時間、並引入新的一致性挑戰。建議在每個 Phase 完成後問自己：「這個新 Agent 解決的問題，是否真的無法透過改進現有 Agent 的 Prompt 來解決？」只有當答案是肯定的，才值得新增一個 Agent。精簡的 Agent 架構往往比臃腫的架構更健壯。
